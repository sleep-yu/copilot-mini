第2页 · 项目背景与价值

🎯 解决什么问题

  • 为个人/小团队提供私有化部署的 AI 对话服务
  • 基于智谱 GLM-4.7大模型，替代高昂的 OpenAI API 成本
  • 支持多会话管理（创建、列表、删除、清空消息）
  • 提供标准 Webhook Hook 接口，便于与现有系统集成

🏠 适合什么场景

  • 企业内部 AI 助手（私有数据不外流）
  • 个人知识库对话机器人
  • 接入企微/飞书等 IM 平台的 AI 服务端
  • 作为 copilot 类产品的轻量级后端核心

👤 用户如何使用

用户打开前端页面 → 注册/登录（JWT鉴权）→ 创建会话 → 发送消息 → 后端调 AI → 返回对话内容 → 前端渲染。整个链路：用户 → 前端 → 后端 → 智谱 AI → 后端 → 前端。

面试时可强调：这是前后端分离的完整全栈项目，RESTful API + JWT 无状态鉴权，水平扩展容易（前端静态部署，后端无状态服务），成本可控（用的智谱 API 比 OpenAI 便宜很多）。

第6页 · 前端关键实现细节

🔧 之前修过的 Bug — stale closure

// ❌ 错误写法（修复前） const sendMessage = () => { fetch('/api/sessions/123/messages', { ... }) .then(res => { setMessages([...messages, res.data]) // 引用了旧 state }) } // ✅ 正确写法（修复后） const sendMessage = useCallback(() => { setMessages(prev => [...prev, res.data]) // 函数式更新 }, [])

问题根因：React 闭包陷阱 — 普通函数捕获的是渲染时的 state 快照，不是最新值。useCallback + 函数式 setState 解决。

🔧 loadOrCreateSession — 错误边界

// ✅ 修复后（catch 块要手动关 loading） const loadOrCreateSession = async () => { try { const session = await findOrCreateSession(); setCurrentSession(session); } catch (err) { setIsLoading(false); // 异常路径也要关 loading toast.error('加载失败'); return; } }

💡 前端可维护性设计

  • 接口层统一封装（减少重复 fetch 代码）
  • loading / error 状态分离（UI 反馈完整）
  • Markdown 渲染（marked 库）— 兼容 AI 返回格式
面试高频追问："React 的 useCallback 什么时候用？" — 回答：作为回调传给子组件或异步函数时，避免闭包捕获旧值。

🔑 鉴权机制

  • bcrypt 密码哈希（10 rounds）
  • JWT 签发（7天过期）
  • 所有 /api/* 路由加 authMiddleware
  • JWT_SECRET 用 IIFE 模式，未配置 throw

🛡️ 异常处理

全局 errorHandler hook：验证错误→HTTP 400，自定义 HttpError→对应状态码，其他→500。响应格式统一：{ code, message, data }。

配置管理：用了 config 库（读 default.json）+ dotenv（.env 覆盖）。踩过坑：config 在 import 阶段读取，AI_API_KEY 要在函数运行时读取，不能用模块级常量。

第9页 · 后端关键实现细节

🔑 JWT_SECRET — IIFE 模式

// ✅ 正确写法：未配置时主动抛错，不 fallback const JWT_SECRET = (() => { const secret = getEnvConfig("JWT_SECRET") as string; if (!secret) { throw new Error("JWT_SECRET not configured"); // 启动时就挂 } return secret; })();

❌ 之前错误写法：用硬编码默认值（如 "secret"），生产环境等于没加密。

🔑 响应状态码 — fail() 显式设置

// ✅ 正确：在 .send() 之前设置 reply.statusCode export const fail = (reply, code, message, statusCode) => { reply.statusCode = statusCode; // 在 send 之前！ return reply.send({ code, message, data: null }); };

踩坑：Fastify 的 preSerialization 钩子会在 .send() 之后覆盖 statusCode，所以要显式在 send 之前设置。

🤖 AI 调用 — 运行时读取密钥

// ❌ 模块级常量：import 时 dotenv 还没执行，读到的是 placeholder const AI_API_KEY = config.get('AI_API_KEY'); // ✅ 函数内运行时读取 async ask({ userId, message }) { const AI_API_KEY = process.env.AI_API_KEY || config.get(...); // 运行时 }

📊 addMessage — AI 对话流程

1

2

AI 回复写入 messages，updatedAt 更新

第11页 · 项目亮点与技术难点

✨ 主要亮点

  • 分层架构：路由/服务/模型三层，职责清晰
  • Fastify 性能：基于 Promise，最大化利用 async/await
  • Schema Validation：请求参数自动校验（内置 schema）
  • JWT 无状态鉴权：水平扩展简单
  • AI 服务集成：统一封装，支持多 AI 后端切换
  • 错误处理体系：全局 errorHandler + 自定义 HttpError

🔒 安全设计

  • bcrypt 密码哈希（防彩虹表）
  • JWT 7天过期 + IIFE 密钥校验
  • CORS 配置（origin: true）
  • 用户隔离：每个 API 校验 userId（不能看别人的会话）
  • Mongoose 参数化查询防注入

🔧 技术难点及解决

1
闭包捕获旧值 — 修复：useCallback + 函数式 setState。React render 是函数，每次渲染快照不同，异步回调拿到的是当次渲染的 state。
2
Fastify 状态码被覆盖 — 修复：reply.statusCode 在 .send() 之前设置。preSerialization 钩子在 send 之后执行，会改写 statusCode。
3
dotenv 加载时机 — 修复：AI 密钥读取从模块级常量移到函数内部（运行时）。import 阶段 dotenv 未执行，process.env 还是空对象。
4
MongoDB 用户权限 — 修复：删除 test 库，用户建在 copilot 库。authSource 必须指向用户实际所在的库。

第12页 · 前端面试题
Q: React 的 useCallback 什么时候用？
考察是否真正理解闭包陷阱和性能优化边界
答：传给子组件的回调、或在异步操作中使用的回调函数，用 useCallback 包裹。本项目 sendMessage 传给 fetch，异步回调里用了 messages state，不包的话会捕获首次渲染的旧值。
Q: React 的 setState 是同步还是异步？
考察对 React 更新机制的理解深度
答：React 18 后 automatic batching 批量异步更新。但关键的是：在 setTimeout / fetch 回调里调用 setState，会在队列中等待下一次渲染时统一更新。直接读取 state 拿不到最新值——这就是 stale closure 的根因。
Q: 如何避免 Token 泄露？
考察安全意识
答：1) Token 存在 httpOnly Cookie 更安全（本项目存 localStorage，是权衡）；2) HTTPS 传输；3) JWT 过期时间控制（7天）；4) 前端统一加 Authorization 头。
Q: fetch 错误如何处理？
考察错误边界意识
答：本项目 loadOrCreateSession 的 catch 里关了 loading + toast + return。错误处理原则：loading 要在所有路径（成功/失败/异常）都关闭，否则 UI 会一直卡着。
前端主动加分项：主动说"还处理了 Markdown 渲染（marked 库），AI 返回的内容可能包含代码块、列表等格式"，说明考虑了AI 内容安全渲染（XSS 防护也可以提）。

第13页 · 后端面试题
Q: Fastify vs Express 区别？为什么选 Fastify？
考察技术选型能力和框架理解
答：1) Fastify 基于 Promise/async，2) 内置 schema validation（不用装 express-validator），3) 更快（基准测试 2x+），4) 插件生态好。本项目参考 cassec-copilot-server 的选择。
Q: JWT 的原理？为什么适合无状态服务？
考察鉴权机制理解
答：JWT = Header.Payload.Signature 三部分，服务端只需要用密钥验签，不需要存 session。任意节点都能独立完成验证，方便水平扩展。本项目每个请求带 Bearer Token，authMiddleware 统一拦截。
Q: MongoDB 和 MySQL 怎么选？为什么要用 MongoDB？
考察数据库选型能力
答：选 MongoDB 的原因：1) messages 是嵌套数组结构，用 Mongoose 的 $push 更新比关联表简单；2) Session 无固定 schema，可能扩展字段；3) Mongoose 文档模型和 TypeScript class 对应，开发体验好。
Q: config 库在 import 阶段读取的问题是什么？
考察对 Node.js 模块系统和配置加载顺序的理解
答：Node.js import 阶段比 require 更早执行，dotenv/config 在 import 之前加载不到 .env，process.env 是空的。解决方案：配置读取放到函数运行时（懒加载）。本项目 AI_API_KEY 用了这个方案。
Q: 什么情况下 HTTP 状态码会被覆盖？
考察 Fastify 生命周期理解
答：Fastify 有 preSerialization 钩子在 .send() 后执行，会改写 statusCode。必须在 .send() 之前 设置 reply.statusCode。本项目 fail() 工具函数显式在 send 前设置。
后端主动加分项：可以说"全局错误处理 hook 是统一的，所有未捕获异常都会走 errorHandler，不会把栈信息泄露给客户端"。体现了安全编码意识。

  • 消息队列解耦：AI 调用异步化，addMessage 写库后发 MQ，后台 worker 调 AI，避免阻塞主请求
  • Redis 会话缓存：热数据放 Redis，减少 MongoDB 压力

⚡ 性能优化

  • 数据库索引：给 (userId, updatedAt) 加复合索引，优化会话列表查询
  • 分页优化：当前用 skip/limit，大页数时慢，可改用游标分页（lastId）
  • 连接池：MongoDB 连接池大小根据并发量调优

🔒 安全加固

  • 敏感操作限流：登录/发消息加频率限制，防滥用
  • XSS 防护：前端对 AI 返回的 HTML/Markdown 做消毒
  • Token 刷新机制：access token 短期 + refresh token 长期
  • 操作日志审计：谁在什么时间操作了什么

🧩 可维护性

  • 接口版本管理：/api/v1/sessions，兼容后续升级
  • OpenAPI 文档：加 Swagger 自动生成接口文档
  • 单元测试覆盖率：当前有测试，可扩覆盖率
  • 环境配置分离：dev/staging/prod 三套 .env

技术上我重点做了三件事：第一是分层架构，路由/服务/模型分离；第二是 JWT 无状态鉴权，用户数据严格隔离；第三是解决了一些实际问题，比如 Fastify 状态码被覆盖、React stale closure 等工程坑。
